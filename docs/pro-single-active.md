Pro uses one active pack. A higher tier replaces the old remaining credits with seven new credits; credits are never added together. Same-tier activation and downgrade are rejected while a pack remains active. Chinese and English tier names come from `shared/pro.ts`.

Legacy packs use the existing priority: highest tier with remaining credits, then oldest creation time and binary ID. Every other pack is permanently retired. Solo storage is normalized and written through its existing ordered persistence queue. Completed-shift receipts are retained. Exhausting the selected pack cannot reveal a previously hidden lower tier.

Online rollout appends `0007_pro_single_active.sql` after the immutable `0000`–`0006` migrations. Apply only this unapplied append to the existing database; never rerun history, recreate tables, clear claims, or disable the migration fence. The append updates existing `revoked_at` fields and adds two atomic entitlement triggers. It creates no new tables or columns and preserves the existing 33 fence triggers, original account/statistics records, room BLOBs and every claim. A frozen database correctly refuses this data migration.

Deploy the append before the new runtime. Before its insertion guard exists, new activation fails closed with `pro_unavailable`/503, while existing reads and claim settlement continue. Legacy readers still filter `revoked_at IS NULL` and see one pack. Legacy activation writers are constrained by the new database guard; an older runtime may surface a generic error for a prohibited same/lower purchase, but cannot grant stacked credits. Rolling back application code must retain the append and all its retired rows/triggers.

Active solo shifts and durable rooms keep the tier/pass frozen at their start. Upgrading does not rewrite those states. Already-held online claims can renew, complete or release on a retired pack; new claims on that pack are rejected. Completing an old solo shift records its receipt without debiting the replacement. New shifts obtain only the current active pack.

Trial requests remain idempotent by their existing `(source, transaction_id)` key. Replaying an old successful request returns current status without reviving the old pack, even after its credits expire. Reusing its request ID for a different tier returns `pro_intent_changed`/409. Existing lifetime earnings, review baselines, suspensions, career totals, room sequence and gameplay schemas are unchanged. No production migration or deployment is performed by these source changes.
