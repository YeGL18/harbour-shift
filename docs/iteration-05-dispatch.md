# 0.5 共享需求、競爭派單及司機紀錄

需求場由房間 seed、共同時間、真實地點分布產生；中心每六個遊戲分鐘平滑移動，範圍約 1–4.5 公里。乘客出現率只由需求決定，增加可接單車輛會降低供需壓力及加成，不會刪走既有乘客 ID。繁忙及高需求地區的估計等候由一分鐘開始。地圖數字、NPC 供應及倍率都是遊戲模型，並非即時平台資料。

0.5 房間由伺服器統一分配真實世界訂單。合法、可接單、上客點附近的車有正機率參與；距離、閒置時間及經伺服器驗證的歷史紀錄只溫和調整權重。新司機樣本不足時採中性權重，低接單率亦不會令機率歸零。同一乘客同時只派給一人；拒絕或過期後可轉派其他附近司機。資訊附近單繼續保留，不能直接當收入。

接近目的地時，繁忙地區可以預接下一張單。它與當前乘客分開，接受後保留當前行程；伺服器會鎖定下一位乘客 ID。取消預接單必須帶正確 tripId，不會取消另一趟行程。補給隊列共用到達時間和 FIFO 服務時段；頭車實際延遲會推遲後車，不移動或瞬移玩家座標。

訪客司機帳戶不需要登入。`POST /v1/drivers` 接受空物件，回傳私密 opaque credential；`GET /v1/drivers/me` 使用 bearer token。建立／加入房間可附 driverCredential；公開名單不含司機憑證或帳戶 ID。客戶端不能提交累積總數。單機紀錄保留於本機，不能影響多人派單權重。

多人累積以 presentedOffers、acceptedOffers、cancelledTrips、completedTrips 的單調增量計算。新 migration `0002_driver_accounts` 把每房間發布代際、不可變 ledger event、帳戶 arithmetic UPDATE 放在同一個 D1 transaction。失敗 CAS 或 SQL failure 不會增加統計；相同或改寫重送的事件只能入帳一次；兩個房間可以安全累加同一帳戶。

傳輸協議維持 protocol 2；新房間明確使用 featureVersion 0.5。舊客戶端加入新房間會得到更新提示，舊 0.4 房間保留舊服務流程並停用預接單，避免送出不認識的排隊狀態。

驗證包括 320 張訂單／8 車公平樣本、同單唯一、轉派、合法車輛篩選、8 車 FIFO 及實際服務延長、Worker 釋放冗餘基礎路網後的派單、下一單 claim/cancel、紀錄高水位、跨房累加、重送、失敗 CAS、整批 SQL 回滾。真實 HTTP／D1 及公網測試結果另列 QA receipt；單元測試不代表公網延遲或手機畫面通過。
